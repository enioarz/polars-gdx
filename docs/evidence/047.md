## Acceptance fixtures (deterministic, independently checkable)

Generator: `crates/polars-gdx/examples/gen_m7_acceptance.rs` (gdxrs
core writer). Values are `ordinal % 1000`; keys are unique ascending
tuples, so expected rows, IDs and value sums are computable
independently of either backend.

| Fixture | Recipe | Size (measured) | Size gate (> 4 GiB / logical > 4x cap) |
| --- | --- | --- | --- |
| `record-raw` | 400,000,000 eighteen-dim records, 2^10 x 5^8 unique ascending key tuples, ~120 logical bytes/row, uncompressed | **4.387 GiB** | pass (raw physical) |
| `record-zlib` | the same 400M records, zlib-compressed | **0.526 GiB** | logical pass (compressed physical may fit RAM, per the contract) |
| `metadata` | 72,000,000 UELs with 63-byte labels (64 logical bytes each) + a 10,000,000-record sparse symbol using every 7th UEL | **4.38 GiB** | pass (metadata physical) |

**Documented deviation**: the contract's 80M-record recipe encodes to
only 0.88 GiB in the compact GDX v7 format (~11.8 bytes/record
physically for 17-dim integer keys), failing the required physical
> 4 GiB gate. The record fixtures therefore scale to 400M records
(2^10 x 5^8) to satisfy the physical size gate; the logical sizes far
exceed 4x the cap either way. Generation: record-raw 65.9 s,
record-zlib 57.4 s, metadata ~21 min (72M labels).

## Capped-process findings (measured, Linux x86_64)

1. **glibc malloc arenas**: with the default arena count, the polars
   streaming engine's fixed VmPeak reaches ~1,009 MiB — right at the
   1 GiB RLIMIT_AS cap — while RSS stays at ~63 MiB. The capped
   qualification therefore configures `MALLOC_ARENA_MAX=2`
   (contract §6: "configure other runtime pools explicitly and record
   their settings"), measuring VmPeak ~346 MiB with identical RSS.
   Without this setting the second acceptance scenario aborts with a
   raw allocation failure under the cap.
2. **pyarrow cannot map under the cap**: the pyarrow-backed
   `GdxrsBatchCursor.__next__` fails to map `libarrow.so` under the
   1 GiB RLIMIT_AS once polars is loaded. The capped acceptance uses
   the Arrow C Data Interface capsule path (`next_stream()` +
   `pl.from_arrow`), which never creates pyarrow objects — the same
   path the lazy source uses in production for engine-thread safety.
3. **Core capped-scan confirmation** (single-trial probe, full
   400M-record raw fixture, enforced 1 GiB RLIMIT_AS,
   POLARS_MAX_THREADS=2, MALLOC_ARENA_MAX=2): **400,000,000 rows**,
   value sum **199,800,000,000** — exactly the independently computed
   expectation — first batch **0.71 s**, full scan **276.6 s**, peak
   RSS **342 MiB** (under the 512 MiB ceiling; input 4.3x the process
   cap).

## Capped streaming acceptance (scenario definitions)

Seven scenarios × three trials per fixture, each against independently
computed expectations (not backend-to-backend agreement):

1. `full-noncollecting-modeB` — the complete stream through a
   noncollecting sink (`collect_batches`), exact row count and value
   checksum.
2. `projection-value-only` — projection pushdown delivers only the
   value column.
3. `sparse-residual-head3` — a sparse residual predicate with a short
   global limit (expected values 996, 997, 998).
4. `cancel-after-first-batch` — cancellation stops and joins at the
   acknowledged prefix (decoded rows far below the total).
5. `zero-limit` — nothing decoded.
6. `modeA-dictionary-admission` — the 72M-label metadata dictionary
   must be rejected clearly; the small record dictionaries must admit.
7. `ordered-head5-independent` — exact ordered IDs, values and schema
   vs the generator recipe.

Per-trial timings, VmHWM/VmSize and explicit cap pass/fail are retained
in the structured JSON reports (`.work/acceptance/report-*.json`;
generator/runner sources are committed, the fixtures and reports are
work-tree artifacts recorded by hash here).

## Backend comparison

The legacy and gdxrs backends are compared on equivalent decoded work
by the existing differential suites (tasks 042–046): identical rows,
order and schemas across all plan shapes, with the documented
projection differences (UNDEF/NA/acronyms: null under gdxrs vs
NaN/native acronym numbers under legacy; EPS -> +0.0 counted). The
legacy backend remains the default; the migration decision and its
gates are recorded in [m7-migration-matrix.md](m7-migration-matrix.md).

## Deviations, unrun cases and limits

- The record fixtures deviate from the contract's 40M/80M-record recipe
  (400M records) because the compact GDX encoding fails the physical
  > 4 GiB gate at the recipe's counts — documented above.
- The contract's 144M-UEL metadata recipe was executed at 72M UELs
  (the smaller of the two recipe sizes).
- macOS/Windows functionality and OS caps: provided by the committed
  platform-matrix CI workflow, not executed in this Linux-only sandbox;
  OS-capped measurements remain Linux-only per the contract ("initial
  enforced OS-cap measurements target Linux only").
- No universal speedup claim: the single-trial probe reports one
  measured full scan (276.6 s for 400M rows); three-trial medians are
  in the structured reports.
- No default-backend change and no `gdx-sys` removal: the migration
  matrix documents the separately reviewable migration change and its
  gates.
