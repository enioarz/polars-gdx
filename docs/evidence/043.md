## Deliverables

- `key_mode` parameter on `scan_gdx`/`read_gdx` (`"enum"` default,
  `"uel_id"`; gdxrs backend only) and on the gdxrs `read_arrow`. The schema
  is chosen before execution and preserved across empty results, zero
  limits, partitions and repeated scans; it is never silently changed on
  admission failure.
- Mode A (`"enum"`): unchanged budget-admitted full-dictionary Enum
  (042 admission: simultaneous string cache + Arrow values + temporaries,
  checked before decoding). Labels decode strictly as UTF-8; invalid bytes
  are rejected before any output (no replacement characters).
- Mode B (`"uel_id"`): the original one-based UEL IDs as plain `UInt32`
  key columns. No label is ever decoded or materialized: mode B performs
  no dictionary admission at all, so files whose dictionary exceeds the
  budget still stream. Batch-local category codes cannot be reinterpreted
  as global IDs because mode B has no categories — the integers are the
  original IDs — and mode A's Enum physicals are the global 0-based UEL
  numbers over the full table (asserted: mode B IDs == mode A physicals+1).
- `GdxrsReader.resolve_labels(ids)`: the contract's bounded resolver.
  Returns an Arrow table with `uel_id: UInt32` and `label: Binary`,
  preserving request order and duplicates with the exact original bytes.
  Zero/out-of-range IDs reject the whole request with `ValueError` before
  any result; the conversion allocation (collected buffer + Arrow
  offsets/values/validity + ID column, all simultaneous copies) is admitted
  against `dictionary_budget_bytes` before any partial table can be
  returned. Labels are fetched through the core's paged `UelLabelCursor`
  (two-page cache) — no full dictionary is materialized.
- `GdxrsReader.label_ids(labels)`: bounded label→ID lookup (core
  `lookup_labels`, exact UTF-8 byte matching) used for ID-mode predicate
  translation without materializing the dictionary.
- String filters in either mode: `key_filter` labels and `col(key) ==
  "label"` predicates encode as UTF-8 and match exactly; in ID mode the
  re-applied predicate compares the resolved integer IDs. Polars does not
  plan String lists against UInt32 columns, so `is_in` predicates in ID
  mode use integer IDs (documented in the `scan_gdx` docstring).
- Fixtures (generator `crates/polars-gdx/examples/gen_m7_fixtures.rs`,
  gdxrs core writer): `m7-dictionary.gdx` (aa,bb,cc,dd IDs 1-4; P records
  (1,10),(2,20),(3,30),(4,40); ZEROS with +0.0/-0.0), `m7-labelbytes.gdx`
  (raw label bytes `61 61` and `ff 62`, values 10, 20) and
  `m7-labels20k.gdx` (20,000 labels, 20,000 records) with SHA-256 digests
  pinned in `tests/test_m7_task043.py`.

## Ownership and unavoidable copies

- Mode A retains two simultaneous dictionary copies by design (the cached
  `Vec<String>` table and the shared Arrow `StringArray` used as every key
  column's dictionary values) plus one transient values copy during the
  Arrow build; all are charged by the 042 admission estimate before
  allocation. The dictionary is owned by the `GdxrsReader` and shared by
  reference across batches; caller-retained output is outside the envelope.
- Mode B owns no dictionary at all: key columns are freshly built `UInt32`
  buffers of the selected rows, charged only by the caller-retained output.
- `resolve_labels` owns one collected label buffer plus the returned Arrow
  arrays; both are admitted together before allocation, and the paged core
  cursor bounds its own cache under the core root budget.
- Core decoder batches, scratch (domain enumeration) and the adapter
  conversion buffers remain under the core `OpenOptions` root budget;
  Polars/Python runtime overhead is accounted separately per contract §6.

## Frozen expectations asserted (tests/test_m7_task043.py)

Dictionary identity (m7-dictionary.gdx): mode A labels/physical codes
(aa..dd / 0..3) and values 10..40; mode B IDs 1..4; global `head(3)`
returns IDs 1,2,3 in both modes (not per batch); repeated scans identical;
empty filters and zero limits preserve the planned schema. Label bytes
(m7-labelbytes.gdx): mode A fails with a label-encoding error before
output; mode B returns IDs [1,2] with values [10,20] without decoding; the
UTF-8 filter `aa` matches only ID 1; `resolve_labels([2,1,2])` returns
(2, b'\xffb'), (1, b'aa'), (2, b'\xffb') in order with schema
{uel_id: UInt32, label: Binary}; IDs 0 and 3 reject the whole request with
ValueError; an over-budget request fails before any partial table.
Conversion: ZEROS projects +0.0/-0.0 with bits 0000000000000000 /
8000000000000000 (the gdxrs writer's Preserve policy keeps signed zero on
disk). Admission and bounded streaming: a tiny budget rejects mode A
before output with zero decoded rows while mode B streams the same
growing 20,000-label table without materializing any category; mode A
under the default budget agrees row-for-row with mode B (IDs ==
physicals+1). Empty/scalar symbols keep the planned enum-or-UInt32/Float64
schema in both modes. `key_mode` validation rejects unknown values and the
legacy backend rejects `"uel_id"` explicitly.

## Deviations and scope notes

- `is_in` predicates in ID mode take integer IDs: Polars refuses to plan
  String lists against UInt32 columns before the adapter sees the
  predicate. String `key_filter` and `==` predicates keep exact byte
  matching in both modes as the contract requires; the docstring and the
  test document the Polars limitation.
- Batch-level disjointness and `batch_size` delivery are task 044; this
  task fixes the schemas, modes and resolver, and asserts cross-mode
  identity on the single materialized batch the current adapter produces.
- Full OS-capped end-to-end qualification remains task 047; nothing in
  this task claims a memory measurement beyond the local admission checks
  recorded above.
