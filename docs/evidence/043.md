## Deliverables

- `key_mode` parameter on `scan_gdx`/`read_gdx` (`"enum"` default,
  `"uel_id"`; gdxrs backend only) and on the gdxrs `read_arrow`. The schema
  is chosen before execution and preserved across empty results, zero
  limits, partitions and repeated scans; it is never silently changed on
  admission failure.
- Mode A (`"enum"`): unchanged budget-admitted full-dictionary Enum
  (042 admission: simultaneous string cache + Arrow values + temporaries,
  checked before decoding). Labels decode strictly as UTF-8; invalid bytes
  are rejected before any output (no replacement characters).
- Mode B (`"uel_id"`): the original one-based UEL IDs as plain `UInt32`
  key columns. No label is ever decoded or materialized: mode B performs
  no dictionary admission at all, so files whose dictionary exceeds the
  budget still stream. Batch-local category codes cannot be reinterpreted
  as global IDs because mode B has no categories — the integers are the
  original IDs — and mode A's Enum physicals are the global 0-based UEL
  numbers over the full table (asserted: mode B IDs == mode A physicals+1).
- `GdxrsReader.resolve_labels(ids)`: the contract's bounded resolver.
  Returns an Arrow table with `uel_id: UInt32` and `label: Binary`,
  preserving request order and duplicates with the exact original bytes.
  Zero/out-of-range IDs reject the whole request with `ValueError` before
  any result; the conversion allocation (collected buffer + Arrow
  offsets/values/validity + ID column, all simultaneous copies) is admitted
  against `dictionary_budget_bytes` before any partial table can be
  returned. Labels are fetched through the core's paged `UelLabelCursor`
  (two-page cache) — no full dictionary is materialized.
- `GdxrsReader.label_ids(labels)`: bounded label→ID lookup (core
  `lookup_labels`, exact UTF-8 byte matching) used for ID-mode predicate
  translation without materializing the dictionary.
- String filters in either mode: `key_filter` labels and `col(key) ==
  "label"` predicates encode as UTF-8 and match exactly; in ID mode the
  re-applied predicate compares the resolved integer IDs. Polars does not
  plan String lists against UInt32 columns, so `is_in` predicates in ID
  mode use integer IDs (documented in the `scan_gdx` docstring).
- Fixtures (generator `crates/polars-gdx/examples/gen_m7_fixtures.rs`,
  gdxrs core writer): `m7-dictionary.gdx` (aa,bb,cc,dd IDs 1-4; P records
  (1,10),(2,20),(3,30),(4,40); ZEROS with +0.0/-0.0), `m7-labelbytes.gdx`
  (raw label bytes `61 61` and `ff 62`, values 10, 20) and
  `m7-labels20k.gdx` (20,000 labels, 20,000 records) with SHA-256 digests
  pinned in `tests/test_m7_task043.py`.

## Ownership and unavoidable copies

- Mode A retains two simultaneous dictionary copies by design (the cached
  `Vec<String>` table and the shared Arrow `StringArray` used as every key
  column's dictionary values) plus one transient values copy during the
  Arrow build; all are charged by the 042 admission estimate before
  allocation. The dictionary is owned by the `GdxrsReader` and shared by
  reference across batches; caller-retained output is outside the envelope.
- Mode B owns no dictionary at all: key columns are freshly built `UInt32`
  buffers of the selected rows, charged only by the caller-retained output.
- `resolve_labels` owns one collected label buffer plus the returned Arrow
  arrays; both are admitted together before allocation, and the paged core
  cursor bounds its own cache under the core root budget.
- Core decoder batches, scratch (domain enumeration) and the adapter
  conversion buffers remain under the core `OpenOptions` root budget;
  Polars/Python runtime overhead is accounted separately per contract §6.

## Frozen expectations asserted (tests/test_m7_task043.py)

Dictionary identity (m7-dictionary.gdx): mode A labels/physical codes
(aa..dd / 0..3) and values 10..40; mode B IDs 1..4; global `head(3)`
returns IDs 1,2,3 in both modes (not per batch); repeated scans identical;
empty filters and zero limits preserve the planned schema. Label bytes
(m7-labelbytes.gdx): mode A fails with a label-encoding error before
output; mode B returns IDs [1,2] with values [10,20] without decoding; the
UTF-8 filter `aa` matches only ID 1; `resolve_labels([2,1,2])` returns
(2, b'\xffb'), (1, b'aa'), (2, b'\xffb') in order with schema
{uel_id: UInt32, label: Binary}; IDs 0 and 3 reject the whole request with
ValueError; an over-budget request fails before any partial table.
Conversion: ZEROS projects +0.0/-0.0 with bits 0000000000000000 /
8000000000000000 (the gdxrs writer's Preserve policy keeps signed zero on
disk). Admission and bounded streaming: a tiny budget rejects mode A
before output with zero decoded rows while mode B streams the same
growing 20,000-label table without materializing any category; mode A
under the default budget agrees row-for-row with mode B (IDs ==
physicals+1). Empty/scalar symbols keep the planned enum-or-UInt32/Float64
schema in both modes. `key_mode` validation rejects unknown values and the
legacy backend rejects `"uel_id"` explicitly.

## Deviations and scope notes

- `is_in` predicates in ID mode take integer IDs: Polars refuses to plan
  String lists against UInt32 columns before the adapter sees the
  predicate. String `key_filter` and `==` predicates keep exact byte
  matching in both modes as the contract requires; the docstring and the
  test document the Polars limitation.
- Batch-level disjointness and `batch_size` delivery are task 044; this
  task fixes the schemas, modes and resolver, and asserts cross-mode
  identity on the single materialized batch the current adapter produces.
- Full OS-capped end-to-end qualification remains task 047; nothing in
  this task claims a memory measurement beyond the local admission checks
  recorded above.

## Second review round on revision 12307f9 and its disposition

1. **[P1] Predicate fallback defeated bounded ID mode** — the residual
   fallback resolved every output label and built per-row strings, so on
   the 20,000-label fixture a label filter plus an always-true value
   condition failed admission under a 1 MiB reader budget. Fixed: the
   fallback now resolves only the label literals appearing in the
   predicate (bounded lookup), and replaces just those key columns with
   sparse label strings — a row's cell holds the label only when the
   row's ID is one of the resolved literal IDs, else null, which is
   exactly the set of rows that could match. No dictionary-scale
   resolution happens in any path. Regression test:
   `test_mode_b_label_fallback_stays_bounded` (label filter + residual
   on the growing fixture, including against a 1 MiB-budget reader).
2. **[P2] Numeric ID predicates broke in the shadow frame** — the
   fallback turned every key column into strings, so
   `(dim_0 == "cc") & (dim_0 == 3)` raised. Fixed: the predicate's
   top-level AND conjuncts are classified per key column; only columns
   with label comparisons are shadowed, so numeric ID predicates on
   other key columns keep evaluating against the UInt32 IDs (verified:
   `(dim_0 == "seattle") & (dim_1 == 3)` on trnsport). Mixing
   string-label and numeric comparisons on the *same* key column cannot
   be evaluated against any single frame and is now rejected with a
   clear ValueError; with predicate pushdown disabled the adapter is
   never consulted and Polars' UInt32/String type error is the
   documented behavior (docstring updated). Regression test:
   `test_mode_b_numeric_key_predicates`.
3. **[P2] Admission followed allocation** — `resolve_labels` built the
   validation vector before checking the budget, so a 128-byte budget
   allowed an 8 MB `Vec<UelId>` before rejection. Fixed: the fixed
   cursor costs plus the request-sized storage (validation vector +
   collected buffer headers) are preflighted against the budget before
   any allocation, so a huge request against a tiny budget is rejected
   before the validation vector exists. The preflight precedes per-ID
   validation, which the regression test proves by asserting the
   request-sized rejection (not the ID-0 ValueError) for a 100,000-ID
   request under a 128-byte budget:
   `test_resolve_labels_admission_counts_all_simultaneous_buffers`.

## Third review round on revision c63db14 and its disposition

1. **[P2] Input extraction preceded admission** — accepting `Vec<u32>`
   let PyO3 materialize the whole request before the method body ran:
   four million IDs allocated 16 MB despite a 128-byte budget. Fixed:
   `resolve_labels` (and, for consistency, `label_ids`) now take the
   **borrowed** Python sequence, read its length, and preflight the fixed
   costs plus the incoming extraction, validation vector and collected
   buffer headers against the budget **before** extracting anything. A
   four-million-ID request under a 128-byte budget is rejected without
   materialization; unsized inputs (generators) are rejected clearly.
   `label_ids`' test now demonstrates the bounded lookup on the growing
   fixture, where a 512 KiB budget rejects the full-dictionary admission
   while the lookup still resolves labels. Regression test:
   `test_resolve_labels_preflights_before_extraction`.
2. **[P2] Disabled-pushdown test passed for the wrong reason** —
   `collect(pred_pushdown=False)` is not a valid argument and raised a
   `TypeError` that the broad `raises(Exception)` caught. Fixed: the test
   uses `collect(optimizations=pl.QueryOptFlags(predicate_pushdown=False))`
   and asserts the intended result — the specific
   `ComputeError` Polars raises for String-vs-UInt32 comparisons — plus
   the positive control that the same plan with integer IDs succeeds with
   pushdown disabled.

`pytest tests/ -q` — **137 passed**; `POLARS_GDX_BACKEND=gdxrs` —
**103 passed, 34 skipped**; gdxrs-only wheel — **85 passed, 40 skipped**.

## Review findings on revision abaa633 and their disposition

1. **[P1] Resolver admission undercounted memory** — one million IDs passed
   a 40 MiB budget while needing at least 56 MB of simultaneous buffers.
   Fixed: the `resolve_labels` estimate now charges every simultaneously
   live allocation — validation storage (`Vec<UelId>`), the collected
   `Vec<Vec<u8>>` buffer (headers + heap payload with allocator
   granularity), the Arrow BinaryArray (i32 offsets + values + validity),
   the borrowed-slice vector, one transient values-buffer copy, and the
   returned UInt32 column — and checks the fixed cursor costs (64 KiB)
   against the budget before anything is allocated or fetched. Verified
   locally on a generated one-million-label file: the request now
   estimates ~120,857,210 bytes and is rejected against a 40 MiB budget,
   while the default budget resolves all 1,000,000 rows. Regression test:
   `test_resolve_labels_admission_counts_all_simultaneous_buffers`
   (fixed-cost rejection plus a 20,000-ID request whose ~2.2 MB of
   simultaneous buffers is rejected under a 1 MiB budget and resolved
   under the default).
2. **[P2] ID-mode label predicates depended on pushdown** —
   `dim_0 == "cc"` succeeded alone, but adding a residual condition
   (`value > 0`) left the untranslated string comparison to Polars, which
   cannot compare String literals against UInt32 columns. Fixed: when a
   predicate in `uel_id` mode references key columns with string label
   literals but is not fully translatable, the adapter evaluates the whole
   predicate against a shadow frame whose key columns hold the exact label
   strings (resolved through the bounded resolver; invalid UTF-8 labels
   decode to null and never match), and filters the ID frame with the
   resulting mask — the same rows as the pushed-down path.
   `is_in` with String lists cannot plan against UInt32 columns at all
   (Polars schema validation happens before the adapter is consulted), so
   it raises the same documented type error with or without residuals;
   integer IDs remain the documented form. Regression test:
   `test_mode_b_key_label_predicates_consistent_with_residuals`.
3. **[P2] Signed-zero test accepted incorrect output** — the assertion
   packed the literal constants `(0.0, -0.0)` instead of the returned
   values, so simulated `[+0.0, +0.0]` output passed. Fixed: the returned
   values' packed bytes are compared against the expected bit patterns
   `0000000000000000` / `8000000000000000`, plus a sign check via
   `math.copysign`.

Post-fix verification at the new head: fmt/clippy/`cargo test --workspace`
clean; `pytest tests/ -q` — **134 passed**; `POLARS_GDX_BACKEND=gdxrs` —
**100 passed, 34 skipped**; gdxrs-only wheel — **82 passed, 40 skipped**.
