# Task 044 — Cursor-backed streaming batch source (evidence)

Task: gdxrs `tasks/044-polars-streaming-batch-source.md` (gdxrs PR #34).
Deliverable: replace the eager full-symbol accumulation of the gdxrs
backend with a real cursor-backed batch source that honors `batch_size`,
enforces the separate byte budget, emits incrementally, and gives every
yielded batch valid owned data after the lending core cursor advances or
closes.

## Deliverables

- `GdxrsBatchCursor` (`crates/polars-gdx/src/gdxrs_backend.rs`): a
  `#[pyclass]` wrapping the core's lending `ScanCursor`. `__next__`
  advances the core cursor, copies the decoded rows into a fresh,
  self-owned Arrow RecordBatch and returns it; a previously yielded batch
  stays valid after the cursor advances or closes (the lending view is
  copied out within the `__next__` call — no cross-call borrowing).
  `scan_statistics()` reports per-cursor projection counters plus core
  decoded rows (preserved across `close()`); `close()` stops at the
  acknowledged prefix and releases the core decoder and batch buffers;
  `Drop` closes too. No universal zero-copy is claimed: each batch owns a
  fresh conversion of the core view, and the enum-mode dictionary values
  are shared by reference (the only reuse).
- `GdxrsReader.scan_batches(...)`: same symbol resolution, key modes,
  filters, admission-before-decoding and value projection as
  `read_arrow`, but returns the cursor. `batch_rows` is honored as the
  agreed maximum rows per emitted batch by scaling the core
  `ScanOptions.batch_bytes` to `batch_rows × row payload` (4 bytes per
  key dimension + one 16-byte typed value), clamped to the core's
  separate byte budget (`maximum_batch_bytes`, 64 KiB default) — so wide
  rows yield fewer rows per batch automatically, and a huge requested
  batch size still cannot exceed the byte budget.
- Python layer (`python/polars_gdx/lazy.py`): the gdxrs source now
  streams — `scan_gdx`'s IO callback iterates the cursor and converts
  each batch with the declared schema, applying predicates, the
  ID-mode shadow fallback, projections and the global accepted-row limit
  per batch. A residual-predicate `head(n)` tracks the remaining rows
  across batches and closes the cursor once satisfied. `batch_size` from
  Polars (default 100000) is passed through as `batch_rows`;
  `collect_batches(chunk_size=...)` is the noncollecting sink. The legacy
  backend still emits one batch and ignores `batch_size` (unchanged).
- `read_arrow` remains the single-batch Reader-level API (legacy parity,
  used by tests and the resolver paths); its internals were refactored
  only to share the dictionary with the cursor.

## Acceptance criteria and their tests (tests/test_m7_task044.py)

- **No hidden full-symbol prescan**: `test_first_batch_does_not_prescan_the_symbol`
  — after two 100-row batches of the 20,000-row fixture, exactly 200 rows
  are decoded (the serial core scan is strictly incremental; no index
  build occurs in this mode, so no separate index-build/strict-validation
  cost exists to distinguish — the `index` feature is not used).
- **Native expectations at one-row/uneven/large batch sizes**:
  `test_batch_sizes_match_native_expectations` (chunk sizes 1, 2, 3,
  1000 → exact batch heights, concatenated batches equal the eager
  single-batch read and the mode-B ID frames) and
  `test_streaming_matches_eager_and_legacy` (semantic fixture specials
  and trnsport symbols, with the documented legacy projection
  differences compared explicitly).
- **Frozen dictionary identity**:
  `test_dictionary_identity_batches_are_frozen` — batch_size=2 emits
  [aa,bb] / [cc,dd] in mode A with all four categories declared in
  registration order per batch, and IDs [1,2] / [3,4] in mode B;
  `test_global_head_limit_across_batches` — head(3) returns IDs 1,2,3
  globally, not per batch.
- **Zero-column projections and empty symbols**:
  `test_zero_column_projection` (a `select()` projection completes and
  produces the empty (0, 0) frame) and `test_empty_symbols_keep_planned_schema`
  (zero batches, planned enum/UInt32 schema preserved, deterministic
  repeated scans).
- **Batch lifetime safety**:
  `test_retained_batch_survives_cursor_advance_and_close` — batches held
  across cursor advance and close are byte-identical afterwards, both as
  pyarrow batches and as polars frames.
- **Bounded producer buffering and backpressure**:
  `test_noncollecting_sink_streams_incrementally` — a noncollecting sink
  (`collect_batches`) serves consumed prefixes correctly. The ADAPTER's
  producer is pull-driven and holds one in-flight batch (proven at the
  cursor level); on top of that Polars' engine applies its own **bounded
  morsel prefetch** — it passes its default `batch_size` (100000), not
  the sink's `chunk_size`, and buffers a bounded number of produced
  batches ahead of the consumer (measured 6,552 rows decoded after
  consuming 1,000 in this environment; the reviewer measured 16,380).
  Production therefore stays bounded but is not exactly consumer-paced;
  the corrected claim is documented in the test and here. Caller
  `.collect()` is the explicit materializing operation.
  `test_early_sink_exit_stops_the_producer` — breaking out of the sink
  stops the scan at the acknowledged prefix (200 rows decoded after four
  50-row batches, preserved across close).
  `test_residual_predicate_head_is_global_across_batches` — a residual
  predicate with a global head limit stops the streaming scan once the
  accepted rows are delivered.
- **Separate byte budget for wide rows**:
  `test_byte_budget_bounds_rows_per_batch_for_wide_requests` — a
  requested batch size of 1,000,000 rows yields ~3,276-row batches
  because the core's 64 KiB batch payload cap bounds the 20-byte row
  layout.
- **Scalars and specials across batches**:
  `test_scalar_and_special_values_stream_correctly`.

## Ownership, copies and deviations

- Every emitted batch owns a fresh conversion of the lending core view
  (keys, values and the Float64 projection); the only shared allocation
  is the enum-mode dictionary values array, shared by reference with the
  reader and identical for every batch. No universal zero-copy conversion
  is claimed or tested.
- The producer holds at most one in-flight batch; Polars pulls batches
  through the IO-source generator, so backpressure is inherent to the
  pull model (no queue exists yet — the bounded producer queue with
  worker admission is task 046).
- The legacy backend keeps its single-batch behavior and ignores
  `batch_size`; migrating it is out of scope for this task.
- Memory measurements: not measured (task 047 adds the OS-capped
  streaming qualification); the bounded-row/byte batch behavior is
  verified functionally as above.
- GIL handling is unchanged (held during batch production); release
  rules are task 046.

## Review findings on revision e89b2a4 and their disposition

1. **[P1] Early consumer exit could abort the interpreter** — consuming
   one `collect_batches` batch, deleting the iterator and exiting
   reproduced SIGABRT (10/10 in the reviewer's environment; reproduced
   here intermittently — 2-9 in 12 trials depending on the variant —
   once the exact combination was isolated). Root cause, found by
   systematic isolation: the SIGABRT (`FATAL: exception not rethrown`,
   a glibc thread-cancellation unwind failure on a native thread with no
   Python frame) occurs when **pyarrow objects are created on Polars'
   streaming engine thread** and the source generator is left suspended
   at process exit — reproduced WITHOUT any GDX code (a plain polars IO
   source building `pa.record_batch` per batch on the engine thread
   aborts 3/14). The abort is specific to the streaming engine (the
   in-memory engine never aborts) and to sources that create pyarrow
   objects per batch; plain generators and pure-pyo3 sources are safe.
   Fix: the streaming source no longer creates any pyarrow object.
   `GdxrsBatchCursor.next_stream()` returns a `GdxrsArrowStream` holder
   exporting the batch through the **Arrow C Data Interface**
   (`__arrow_c_stream__`, a `PyCapsule` whose release runs pure Rust
   code); the lazy source consumes it with `pl.from_arrow(holder)` +
   `.struct.unnest()` and re-applies the declared schema by exact cast
   (dictionary keys arrive as Categorical and cast to the declared Enum
   — the dictionary is the full UEL table in file order, so values and
   physicals are preserved; mode B columns are identical no-op casts).
   Defense in depth: the emission loop wraps in `try`/`finally` with
   explicit `cursor.close()` on every exit path (skipping the extension
   call if the generator is only finalized during interpreter
   shutdown), and live cursors are tracked in a module registry closed
   by an `atexit` hook, so production is stopped and joined before
   interpreter shutdown. Verified: 0/20 aborts on both reproductions
   (previously up to 9/12 and 7/10). Subprocess regression tests run the
   reviewer's exact early-exit reproduction and a residual-filter
   `head()` variant, three trials each, asserting exit code 0:
   `test_early_consumer_exit_terminates_cleanly`.
2. **Backpressure claim was wrong** — after consuming 1,000 rows of the
   sink and pausing, the source had produced 16,380 rows (reviewer;
   6,552 measured here): Polars passes its default `batch_size` (100000),
   not the sink's `chunk_size`, and its engine prefetches a bounded
   number of morsels beyond the consumer. The "producer never runs ahead
   / buffers only the current batch" claim was corrected: the adapter's
   producer is pull-driven with one in-flight batch (cursor-level proof
   unchanged), and Polars' bounded prefetch is documented in the test and
   the acceptance section above.
