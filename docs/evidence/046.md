# Task 046 — Scan lifecycle, threads and cancellation (evidence)

Task: gdxrs `tasks/046-polars-scan-lifecycle.md` (gdxrs PR #34).
Deliverable: explicit thread options and the qualified execution policy
integrated with the adapter's lifecycle — fallible close/cancellation
that wakes and joins all owned workers, GIL release under valid
ownership rules, concurrent and repeated scans, and scratch release.

## Deliverables

- **Thread admission** (contract §6): `threads=2..=4` on the gdxrs
  backend runs the core's parallel scan (`scan_selected_parallel`) with
  `ParallelOptions { workers, maximum_in_flight_tasks: workers,
  intervals_per_task: 1, worker_stack_bytes: 2 MiB, admission: Exact }` —
  at most 4 admitted workers, at most one task/batch per worker in
  flight, batches bounded by the reader's 64 KiB byte budget (below the
  contract's 1 MiB cap). Requests above the admission raise `ValueError`
  (never silently clamped); `None`/`0`/`1` stay serial; `"auto"` never
  exceeds the admission and stays serial for small symbols. The legacy
  backend's thread behavior is unchanged.
- **Explicit index mode**: the parallel path builds a checkpoint-index
  sidecar once per reader+symbol (`index_builder`/`finish`, 4096-record
  stride so sub-64k-record symbols keep parallel granularity) at an
  explicit one-pass build cost, then opens a fresh, strictly validated
  (`IndexPolicy::UseIfValid`) `CheckpointIndex` per scan — concurrent
  scans hold independent handles and repeated scans reuse the build.
  Sidecars live in a per-reader temp directory removed on
  `close()`/drop. No hidden index build exists in the serial path.
- **No unbudgeted pool nesting**: core workers spawn inside
  `next_batch` and join before it returns, so a Polars engine thread
  driving the source never runs nested worker pools. The legacy
  wrapper's global-lock and unsafe-`Send` assumptions are not imported
  (the gdxrs module contains no `unsafe` except the documented
  `Send`/`Sync`/`repr(transparent)` capsule wrappers).
- **GIL release**: `__next__`/`next_stream` release the GIL around core
  production (`py.allow_threads`) — the core owns its data and no Python
  object is touched during I/O, decode or worker joins — so other
  Python threads proceed during scans. Capsule/Arrow conversion happens
  with the GIL held.
- **Fallible close/cancellation**: `close()` (both cursor kinds) wakes
  blocked producers/consumers and joins all owned workers, idempotently;
  `cancel()` requests parallel cancellation and joins. The streaming
  generator's `finally` closes the cursor on every exit path (consumer
  drop, sink exceptions, Python cancellation via generator close, early
  limit satisfaction), the live-cursor registry and `atexit` hook stop
  production before interpreter shutdown, and `sys.is_finalizing()`
  guards extension calls during late finalization. Blocked synchronous
  OS reads inside an in-flight worker step cannot be forcibly
  interrupted; cancellation joins the current step (documented in the
  docstring and here).
- **Error propagation**: core/decode/source errors surface as errors —
  never retried through the legacy backend, never replaying
  acknowledged rows; the parallel cursor's sticky errors and
  secondary join/cleanup diagnostics propagate through `close`/`cancel`
  results. Retained batches keep only their documented owners (fresh
  per-batch conversions; the shared dictionary is the only reused
  allocation).
- **Lifecycle counters**: `scan_statistics()` now reports the parallel
  execution counters (`requested_workers`, `admitted_workers`,
  `maximum_buffered_batches`, `peak_ready_batches`, `joined_workers`,
  `cancelled`, `complete`), snapshotted at close/cancel so joins remain
  observable afterwards.

## Acceptance criteria and their tests (tests/test_m7_task046.py)

- **Parallel parity** (`test_parallel_scans_match_serial_exactly[2,3,4]`):
  byte-identical results to the serial read across plain scans, key
  filters, projections, residuals, heads, both key modes and
  trnsport's multi-dimensional symbols.
- **Thread admission** (`test_thread_admission_is_explicit`): 2..=4
  admitted, >4 rejected, None/0/1 serial, `"auto"` capped and
  small-symbol-serial.
- **Lifecycle counters and joins**
  (`test_parallel_lifecycle_counters_and_joins`): admitted concurrency,
  bounded queue pressure (`peak_ready ≤ maximum_buffered ≤ workers`),
  all workers joined, complete/cancelled state.
- **Cancellation** (`test_cancel_joins_workers_and_stops_production`):
  explicit `cancel()` wakes waiters, joins all workers, ends the stream
  without replaying acknowledged rows; idempotent close.
- **Partial output** (`test_partial_output_acknowledges_only_consumed_batches`):
  stopping mid-scan acknowledges exactly the consumed prefix; retained
  batches stay valid after the join.
- **Sink exceptions** (`test_sink_exception_propagates_and_joins`): the
  error propagates, workers join, no retry/replay.
- **Spawn/read/decode/source errors** (`test_error_propagation_from_parallel_scan`):
  truncated/garbage sources and unknown symbols raise clearly.
- **Consumer drop / Python cancellation / shutdown**
  (`test_parallel_early_exit_terminates_cleanly`,
  `test_python_cancellation_via_generator_close`): subprocess
  reproductions with parallel workers exit 0 across repeated trials;
  generator close joins mid-scan.
- **Concurrent scans** (`test_concurrent_parallel_scans_on_one_reader`):
  two parallel cursors (2 and 3 workers) interleave on one reader and
  both deliver full ordered results with their own join counts.
- **Repeated execution** (`test_repeated_parallel_execution_is_deterministic`):
  three repeated parallel scans are identical; the index build is
  reused.
- **GIL release** (`test_gil_released_during_parallel_production`): a
  background Python thread progresses while a parallel scan runs.
- **File/scratch release** (`test_index_sidecars_released_on_reader_close`):
  the index temp directory exists while the reader is open and is
  removed with its sidecar on close.

## Second review round on revision 3b2344b and its disposition

1. **[P1] Early consumer exit still aborted Python** (7/20 serial,
   4/20 parallel in the review) — the state mutex fixed concurrent
   borrowing, but shutdown did not ensure the whole source callback
   finished before interpreter teardown: the atexit drain covered only
   `next_stream()`, so a Polars engine thread could still be executing
   the generator body (Arrow/Polars conversion, residual predicates,
   projection) — or re-entering it after a teardown-time resume —
   against the finalizing interpreter. Reproduced locally under CPU
   contention (2/40 parallel; `FATAL: exception not rethrown` on a
   native thread with no Python frame). Fixed with a two-part shutdown
   protocol in the Python layer:
   - a `_SHUTTING_DOWN` event set by the atexit hook: streaming loops
     check it before every extension call, so a generator resumed
     during teardown executes only the pure-Python flag check, breaks
     and returns — no PyO3 call ever happens on the finalizing
     interpreter;
   - the in-flight count now covers the **whole callback body**
     (increment at loop top, decrement before the `yield`), and the
     atexit hook drains it to zero (sleeping, so the GIL is released)
     after closing the cursors — teardown cannot begin while any
     callback is still executing, and a generator suspended at the
     yield is never counted.
   Verified: 0 aborts in 440 contended trials (110 serial + 110
   parallel early-exit runs twice each, plus 60+60 earlier); plain
   Polars sources remain clean under the same stress. The other two
   findings from the first round (cross-thread cancellation, sidecar
   leak) stayed fixed in focused reruns by the reviewer.

Post-fix verification: fmt/clippy clean; `pytest tests/ -q` —
**207 passed**; `POLARS_GDX_BACKEND=gdxrs` — **173 passed, 34
skipped**; gdxrs-only wheel — **155 passed, 40 skipped**.

## Third review round on revision ce92478 and its disposition

1. **[P2] Shutdown could miss a callback entering production** — the
   shutdown check and the counter increment were separate, so a
   callback paused between them let shutdown return with zero
   registered callbacks while the paused callback resumed into
   `next_stream()` after shutdown. Fixed: the gate and the registration
   are now atomic in `_enter_callback()` under the same lock the
   shutdown hook uses to set the flag — no callback can slip between
   check and increment, and no shutdown can complete its gate while a
   callback is registering. Regression tests:
   `test_shutdown_gate_refuses_new_callbacks` (scans after the flag is
   set yield nothing instead of touching the extension) and
   `test_shutdown_gate_and_registration_share_one_lock` (while the lock
   is held, neither the hook's flag nor a concurrent registration can
   proceed).
2. **[P2] The drain silently expired with callbacks active** — a
   residual callback sleeping 34 s was still active
   (`_IN_FLIGHT == 1`) when the 30 s drain returned. Fixed: the drain
   has **no deadline** — it returns only after confirmed completion
   of every registered callback; blocked synchronous OS reads cannot
   be forcibly interrupted (documented), so shutdown waits for them by
   design. Regression test:
   `test_shutdown_drain_waits_for_confirmed_completion` (the drain
   returns only after a concurrently released registration confirms,
   with the elapsed wait asserted).

Post-fix verification: fmt/clippy clean; `pytest tests/ -q` —
**210 passed**; `POLARS_GDX_BACKEND=gdxrs` — **176 passed, 34
skipped**; 0/40 aborts on both early-exit reproductions (the ordinary

## Fourth review round on revision 4517e72 and its disposition

1. **[P2] Source setup bypassed the shutdown gate** —
   `reader.scan_batches()` (an extension call: admission, index build,
   worker spawn) ran before the first callback registration, so a
   generator paused there let shutdown drain to zero and the paused
   setup resumed into the extension after shutdown. Fixed: the setup
   is gated and registered exactly like a production step
   (`_enter_callback()` before `scan_batches`, `_exit_callback()` in a
   `finally`); a shutdown that has already begun ends the source before
   any extension call. Regression test:
   `test_shutdown_gate_covers_source_setup` (with shutdown begun, a
   parallel scan yields nothing and no index sidecar directory is ever
   created — the setup extension call provably never ran).
2. **[P2] The concurrency test could leave shutdown blocked** — if the
   registration won the race, `_enter_callback()` returned True but the
   test never matched it, leaving the shutdown thread's
   confirmed-completion drain waiting indefinitely. Fixed: the test
   matches a successful registration (`_exit_callback()`) and asserts
   both threads terminate.

## Fifth review round on revision 72bd06f and its disposition

1. **[P2] Predicate planning bypassed the gate** — an ID-mode label
   predicate called `reader.label_ids()` twice during predicate
   planning before the first `_enter_callback()`. Fixed: the whole
   gdxrs callback is now gated and registered at generator entry —
   the registration covers predicate planning, source setup and cursor
   publication, and is released (in a `finally` on every exit path)
   before the streaming loop; suspension points still carry zero
   registrations. A shutdown that has already begun ends the source
   before any extension call, including predicate planning. Regression
   test: `test_shutdown_gate_precedes_predicate_planning` (with
   shutdown begun, an ID-mode label-predicate scan yields nothing and
   the planning spy records no call; normal operation plans and
   matches).
2. **[P2] Shutdown could miss a newly created cursor** — setup
   unregistered before publishing the cursor, so a paused interleaving
   let shutdown return with zero registered callbacks/cursors while
   the new parallel cursor held four admitted workers, zero joined.
   Fixed on both sides: the setup registration now stays held through
   cursor publication (the cursor joins the registry before the
   registration is released), and the shutdown drain closes any cursor
   published while it waits — it loops until callbacks are confirmed
   complete AND the registry is empty, closing late-published cursors
   (joins their workers) before returning. Regression test:
   `test_shutdown_closes_cursors_published_during_drain` (a cursor
   published mid-drain by a registered callback is closed before the
   shutdown thread returns).

## Sixth review round on revision 69c9d8b and its disposition

1. **[P2] The initial sweep could erase an unclosed cursor** —
   publishing a cursor while the first sweep ran let
   `_OPEN_CURSORS.clear()` remove it without closing it (shutdown
   returned with an empty registry and an unjoined cursor). Fixed: the
   sweep and the drain are merged into one loop that removes only the
   PROCESSED snapshot (`difference_update`), so a cursor published
   while the loop runs is closed in a later iteration — never silently
   erased. Regression test:
   `test_shutdown_sweep_does_not_erase_late_published_cursors` (a
   cursor published from inside the sweep's own close() is closed
   before shutdown returns).
2. **[P2] Cancellation during the setup handoff corrupted accounting**
   — a KeyboardInterrupt landing after `_exit_callback()` but before
   `setup_registered = False` made the outer finally decrement again
   (`_IN_FLIGHT == -1`, shutdown waiting indefinitely). Fixed: the
   registration now has exactly ONE cleanup path — the registered
   preamble's `finally` — with no flag handoff after the release, and
   the cursor-cleanup `try`/`finally` is established directly after
   publication, owning every path from the handoff through the
   streaming loop. Regression test:
   `test_preamble_cancellation_releases_registration_once` (a
   cancellation injected in the registered preamble leaves the counter
   exactly at zero, never negative, and normal operation is restored).

## Review findings on revision 346b6e3 and their disposition

1. **[P1] Early consumer exit aborted Python again** (3/10 serial, 2/10
   parallel in the review) — the task-046 GIL release let the `atexit`
   cleanup run *concurrently* with in-flight production, which held the
   exclusive PyO3 borrow, so `cursor.close()` failed with "Already
   borrowed", the atexit hook swallowed the error and active production
   survived into interpreter teardown. Fixed: the cursor's state is now
   interior-mutable (`Arc<Mutex<CursorState>>`) and every method takes a
   **shared** PyO3 borrow — production holds the state lock with the GIL
   released, and close/cancel from any thread acquire the same lock,
   so cleanup waits for the in-flight step and then joins. Verified:
   0/25 aborts on both the serial and the parallel early-exit
   reproductions (previously 3/10 and 2/10).
2. **[P2] Cancellation failed during active production** ("Already
   borrowed", 5/5) — same root cause. Fixed additionally with the core's
   lock-free `ParallelCancellation` handle, captured at cursor creation
   and stored outside the mutex: `close()`/`cancel()` call
   `request_cancel()` first, waking in-flight parallel production from
   any thread without borrowing the scan state, then acquire the lock
   to join. Regression test:
   `test_cancel_from_another_thread_during_production` (producer thread
   drives `next_stream`; main thread cancels; no borrow failure, workers
   join, stream ends without replay).
3. **[P2] Reader destruction leaked index sidecars** — cleanup existed
   only in explicit `close()`. Fixed: the sidecar cleanup is factored
   into `cleanup_index_sidecars()` shared by `close()` and a new
   `Drop for GdxrsReader`, so deleting the reader (with GC) removes the
   index directory and sidecars; a cursor outliving its reader completes
   its scan and releases its own handle on drop. Regression test:
   `test_reader_drop_releases_index_sidecars`.
